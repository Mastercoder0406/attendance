# DECISIONS.md

1. **Indexes.** On `attendance_logs`: Unique (`emp_code` `date`) ensures that no employee can have two attendance records for the date. It also stops punch-ins when requests come in at the same time. The index `(date desc, emp_code)` helps get attendance records sorted by date and supports queries like leaderboards and trends. The index `(status, date desc, emp_code)` helps when filtering by status, such as PRESENT or WFH and sorting by date. The index `(emp_code, punch_in desc)` helps find an employee’s recent punch-in when processing a punch-out. The unique `emp_code` index stops employee codes from appearing. Department-related indexes help find employees by department or look at joining dates. `(Department, joined_on)` is used for that. The decision is to not add another index because the date range is expected to limit the number of records that need to be checked.

2. **Punch-in race.** If two requests check for a record first and both find nothing they might both try to insert a record. This can cause duplicates. This is called a race condition. By using an index on (`emp_code` `date`) MongoDB allows only one insert to go through. The second request gets a DuplicateKeyError, which the application turns into an `HTTP` 409 Conflict response.

3. **Ties.** Imagine a leaderboard with a limit of three employees.. Two employees tie for third place. If you just take the three records, one of the tied employees might get left out. To fix this use MongoDB’s `$rank` operator. It gives the rank to tied values. Then filter using rank <= limit. This way every employee within the ranking limit is included, even if than three records are returned.

4. **Headcount.** If you start counting from the `attendance_logs` collection employees who have never punched in will not show up. Instead the aggregation begins with the `employees` collection. Then it uses `$lookup` to find attendance records for each employee. With `preserveNullAndEmptyArrays` employees without any logs are still kept in the results.

5. **100X data.** As the database grows, calculating summaries from all raw attendance records over and over can become slow. To avoid that a monthly roll-up stores pre-calculated summary data, for each employee. Each month. The application updates this summary whenever an employee punches in or when an attendance record is corrected. This cuts down the amount of data needed for monthly reports. Corrections must update the summary carefully to make sure totals stay accurate.
